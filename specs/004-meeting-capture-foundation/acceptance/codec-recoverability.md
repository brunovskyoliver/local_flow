# Codec recoverability spike (FR-005, T005–T008)

**Run**: 2026-09-18 on the development machine. **Hardware**: `Mac17,2`, Apple M5, 32 GB.
**macOS**: 26.6.2 (25G83). **Toolchain**: Xcode 26.4.1 (17E202), `swiftc -O`.
**Harness**: `spike/codec-spike.swift` driven by `spike/run-spike.sh` (throwaway; not part of
the app). Build products under `build/codec-spike/` (ignored by git).

## Method

Each writer records a 60 s synthesized signal (1 kHz tone at −8 dBFS with ±0.02 white noise,
48 kHz mono Float32) in 4,096-frame blocks paced to real time, and prints bytes on disk and
RSS once per second. The process is killed with `kill -9` at 5, 20 and 55 s (one run per kill
point per writer; nine runs). Each file is then opened and fully decoded in 8,192-frame
blocks through `AVAudioFile`; "recoverable seconds" is decoded frames ÷ sample rate.

Deviation from the task text: no microphone was opened. A terminal harness would need its
own microphone TCC grant, and the property under test (what the container leaves on disk
after SIGKILL) does not depend on where the PCM came from. The production encoder path
(`AVAudioConverter` → AAC-LC → ADTS) is the one exercised here.

Writers and settings:

| Writer | API | Settings | Sync |
| --- | --- | --- | --- |
| ADTS | `AVAudioConverter` to `kAudioFormatMPEG4AAC`, hand-built 7-byte headers, `write(2)` on an owned fd | 48 kHz mono, 64 kbit/s, 8-packet output block | `fsync` every 5 s |
| fMP4 | `AVAssetWriter` (`.mp4`, `movieFragmentInterval = 1 s`, real-time input) | 48 kHz mono AAC 64 kbit/s | writer-owned |
| M4A | `AVAudioFile(forWriting:)` | 48 kHz mono AAC 64 kbit/s | file-owned |

## Results

| Writer | Kill at | Bytes on disk | Playable (`AVAudioFile`) | Recoverable s | Bytes lost | RSS while writing |
| --- | --- | --- | --- | --- | --- | --- |
| ADTS | 5 s | 40,993 | yes | 4.949 | 0 (trailing bytes 0; 232 complete frames) | 14.0 MB |
| ADTS | 20 s | 163,161 | yes | 20.053 | 0 (940 complete frames) | 14.1 MB |
| ADTS | 55 s | 449,719 | yes | 55.040 | 0 (2,580 complete frames) | 14.1 MB |
| fMP4 | 5 s | 42,024 | opens | 0.980 | everything after the first fragment | 20.3 MB |
| fMP4 | 20 s | 164,940 | opens | 0.980 | everything after the first fragment | 20.5 MB |
| fMP4 | 55 s | 450,464 | opens | 0.980 | everything after the first fragment | 18.2 MB |
| M4A | 5 s | 101,532 | no (`AVAudioFile` open error 1685348671) | 0 | all | 14.6 MB |
| M4A | 20 s | 218,472 | no | 0 | all | 14.7 MB |
| M4A | 55 s | 493,168 | no | 0 | all | 14.9 MB |

Raw lines: `build/codec-spike/results.txt` (regenerated by the script).

Observations:

- ADTS lost nothing at any kill point. Whole frames are written in one `write(2)` call per
  encode, so the kill never landed mid-frame; the recoverable duration is the frames written
  before the kill (4.949 s at a 5 s kill is the pacing offset, not loss). The header scan in
  the harness (the same algorithm `ADTSValidator` uses) agrees with `AVAudioFile` on every
  file: `completeBytes` equals the file size.
- fMP4 files open, but `AVAudioFile` only reads the frames covered by the initial `moov`
  duration (the first fragment, 0.98 s). Recovering later fragments would need a separate
  `moof` walk. This is the "writer owns the file handle" concern from research.md in
  concrete form.
- Plain M4A is unplayable after a kill in every run: no `moov` was written.
- RSS is flat within a run for every writer (no growth over 55 s).

## AVQueuePlayer over consecutive ADTS files (T008)

`spike/queue-check.swift` queued
`adts-kill5` then `adts-kill20` in one `AVQueuePlayer`: two items, `currentItem.status ==
readyToPlay`, `rate == 1.0`, `currentTime` advancing (2.85 s after 3 s wall time including
load). `AVURLAsset.duration` reported 4.949 s and 19.797 s; the second is 1.3 % under the
frame-derived 20.053 s because ADTS has no index and AVFoundation estimates duration from
bitrate. Consequence for the detail view: the displayed position and length come from the
database `duration_ms` (frames encoded), not from the asset.

## Screen-recording prompt (T008)

terminal, not the app, so it proves nothing about the signed build. No `Info.plist` key was
added: macOS 14 grants Screen & System Audio Recording through System Settings without a
usage-description key. The live prompt check belongs to T078 on the reference machine.
