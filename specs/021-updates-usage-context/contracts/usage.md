# Usage contract v1

Design contract; endpoints do not exist yet. JSON schemas must be committed before handlers.

## Consent and identity

Existing approved-user/device authentication applies to the `usage` operation on the encrypted session channel. Its `request.action` selects consent/status/deletion/snapshot; `usage_reply` is the sole terminal response. No plaintext client reporting endpoints are added. The server derives user/device identity from the verified session, never payload identity. Disabled by default. A consent grant returns a random epoch UUID; withdrawal invalidates it and drops pending client aggregates. Re-enabling creates a new epoch and never backfills disabled periods. Revoked devices cannot ingest. Delete revokes the current epoch, deletes matching retained data and propagates a tombstone to the dashboard before accepting any new epoch. Preserve bounded epoch tombstones until all 90-day reports expire. Server uses a transactional durable outbox for deletion, and reports deletion pending while the dashboard is unreachable.

## Daily cumulative snapshots

Body: version=1, consent_epoch UUID, rows array (1..100), each with UTC day, monotonically increasing uint64 revision, nonnegative counters for local/remote completed dictations, audio duration in integer milliseconds, plus coverage enum complete/partial. Maximum body 64 KiB. Reject unknown fields, future dates beyond one day and dates older than 90 days. All counters must fit signed 64-bit storage; checked arithmetic rejects overflow. One dictation completion has one stable UUID through retry/fallback; client transaction atomically records completion and updates the applicable day. Remote success counts in remote, remote failure with successful local fallback counts in local. Server operational attempts never enter these dictation totals.

Uniqueness: server-assigned user/device + epoch + UTC day. Higher revision replaces cumulative values; equal revision with different values is a conflict, lower revision is ignored. Counters cannot decrease within an epoch/day. Authenticate before examining duplicate status. Responses distinguish accepted, duplicate, stale, invalid, revoked and busy; unknown capabilities disable export gracefully for old servers.

Client deduplication uses existing persisted dictation IDs plus a bounded completion ledger when needed: 10,000 IDs or 90 days, whichever first. At capacity do not evict live retry IDs silently; mark coverage partial and stop counting new operations until capacity is available. User dictation history deletion cannot cause replay of counted operations. No audio or text enters this ledger.

## Export and hosting

Server exports cumulative snapshots over TLS to `/v1/ingest/usage`, using a dedicated installation-bound credential. Ingestion has no public registration and cannot mutate inference accounts. Use the same revision rules, with installation ID added to the key. Configuration contains an explicit host allowlist; redirects cannot forward credentials. Dashboard login is read-only, restricted to one configured OIDC issuer/subject; its authenticated deletion control creates a server-side request through the reporting control path, never exposes an inference admin token to a browser. Client deletion remains the primary user path.

Cap client storage at 90 daily rows and 10,000 completion IDs per device, plus bounded epoch metadata. Cap server/dashboard at 100 users, 10 devices/user, 90 retained days and 180,000 daily aggregate rows total (includes epochs); 128 MiB usage database budget, separate from accounts and content. One in-flight export, 64 KiB batches, retry 30 s to 1 h, 30 s request timeout. Full stores return busy and mark partial coverage; no dictation backpressure. Tombstone capacity must reserve space for deletion at the supported user/device limit; reject new enrollment/consent if that reserve cannot be maintained. Purge expired rows daily and on startup. Export snapshots by revision with a bounded cursor, not an unbounded job queue.

Never transmit audio, text, window titles, URLs, field context, credentials or arbitrary client strings. Fixed service/outcome/version enums only. The owner view joins account display identity separately; disclose this during consent. Last report is not equivalent to last activity. Offline/disabled/unlinked devices are absent or explicitly incomplete.

## Operational metrics

Optional private scrape endpoint, disabled by default, fixed metric names and bounded service/outcome labels. No user/device labels or request text. Include request duration buckets, queue depth, worker readiness and error counts. An owner-operated OpenTelemetry Collector may scrape/forward; collector failure has no inference effect. Durable user usage never relies on these samples.

## Resolved analysis requirements (normative)

These rules supersede conflicting research proposals. Final bounds are 100 rows/64 KiB, one row/day containing both modes and 90 daily rows/client. Product totals exclude failed/cancelled attempt counters. Reliability uses separate server metrics. Successful duration includes only captured sample-frame duration for the successful logical dictation, never retry wall time or failed attempts.

Count at the first durable history commit of a nonempty successful dictation, independent of insertion success. Rewriting/insertion retries do not count. Freeze account, device and consent grant at recording start; completion counts only if the same account and grant remain active. Enabling consent mid-recording does not count that recording. Atomic accounting must share the completion transaction where feasible; reporting failure must not roll back saved text, and must instead expose partial coverage.

Each device has one current monotonic reporting epoch (uint64) plus a random grant UUID. Ingestion, export and dashboard rows carry both. Withdrawal and revocation advance the epoch and disable its grant before any new export; deletion additionally advances a deletion cutoff covering ALL prior retained epochs for the selected device or every device of a selected user. Re-enabling requires a new acknowledged grant. Account identity never comes from client payloads.

Control records contain device epoch, enabled state, deletion cutoff and revision. They take priority over data. The dashboard stores latest state and rejects older epochs. A deletion removes all rows/queued exports at or below its cutoff; delayed older exports cannot recreate them. In-flight changes serialize with control application. Until downstream control acknowledgment, the UI states withdrawal/deletion propagation pending; never claim hosted removal complete early. A single bounded source exporter rechecks current grant state immediately before dispatch and discards superseded queued snapshots. Dashboard ingestion authenticates the installation and commits control plus rows in one transaction. It rejects any older epoch/revision/cutoff after the newer control lands. An already in-flight report may arrive before its withdrawal/deletion control; the source explicitly shows propagation pending until control acknowledgment. This is eventual cross-host propagation, not instantaneous distributed revocation. Inference authorization still revokes independently. Race tests must prove that delayed data cannot resurrect rows after the control applies, regardless of arrival order.

Cap reporting identity metadata at 100 users and 1,000 device slots INCLUDING retired/deleted devices awaiting expiry/acknowledgment. Each slot stores only its latest epoch, grant and pending control; no per-grant queue or tombstone growth. At most 1,000 control/outbox slots, 1,000 grant states and 1,000 deletion cutoffs; user deletion fans out only across those slots. Coalesce controls by greatest epoch/cutoff, preserving deletion intent. Reserve control storage at grant admission. When full, reject only new reporting grants with reporting_busy, never inference enrollment, authentication or dictation. Withdrawal/deletion of existing grants uses reserved slots. Retire a slot only after downstream acknowledgment and the 90-day replay horizon; backups must replay deletion controls before serving. Epoch overflow disables reporting until administrative reset after retention, never wraps.

Directory projection is part of authenticated server export: installation-scoped user UUID, display label (at most 128 Unicode scalars/512 UTF-8 bytes), revision and removed flag. At most 100 rows; no email/OIDC subject/provider token. Use an account display name or opaque fallback, only for users with retained consented usage. Delete projection when user usage is erased; stale directory updates follow the same control revision barriers. Dashboard never reads the inference account database. Fixed request concurrency is four globally and one per device; directory and control bodies use the same 64 KiB maximum. Response sizes are capped identically.

## Implemented control binding and browser transport

Consent controls `withdraw`, `delete_device` and `delete_user` carry the recording/account binding's expected numeric `epoch` and random `grant`. The server accepts the current grant, or one bounded previous-grant binding while disabled for retry/deletion escalation. Re-enabling invalidates that previous binding. Repeated deletion returns the same pending revision until downstream acknowledgment; it must not advance the epoch on every retry. Never-enabled devices have no retained usage to delete. `status` and `enable` omit binding fields. `usage_reply` is the sole terminal channel response.

The first browser owner login provider is Google, with the exact configured issuer `https://accounts.google.com` and subject. Client enrollment providers are unchanged. The optional source exporter polls authenticated `/v1/control/deletions` for owner-originated reporting-only erasure requests. At most one request per retained user is queued (100 total), and controls do not grant inference administration access. Human-readable directory names are not inferred from an account field that may contain email; the implemented fallback is `User <opaque UUID prefix>`.
