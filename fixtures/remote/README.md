# Remote channel fixtures

Shared by flowd (`server/internal/remote`, `server/internal/speech`, `server/internal/oidc`) and the macOS client tests (`RemoteProtocolTests`, `RemoteChannelTests`, `SpeechWorkerFramingTests`) for Feature 014. The normative rules are in `specs/014-remote-dictation-server/contracts/`.

**Nothing in this directory is a production secret.** Every key here is test-only: the HPKE keys are derived from public labels, and the RSA signing key exists only so a debug-build issuer can mint ID tokens for integration tests. None of them protects anything, and no production build accepts them.

## `hpke-vectors.json`

One complete channel exchange with fixed static keys, so both implementations can check they produce and accept the same bytes. Generated by `server/internal/remote/channel_vectors_test.go`; `go test ./internal/remote -run TestHPKEVectors -update` (from `server/`) rewrites it, and the same test without `-update` fails unless the file reproduces byte for byte. The ephemeral keys come from Go's seeded test randomness (`testing/cryptotest`), so a Go release that changes how HPKE draws randomness may need a regeneration; the frames stay valid either way.

Every byte string is lowercase **hex**. Suite: HPKE base mode, DHKEM(X25519, HKDF-SHA256) `kem_id` 0x0020, HKDF-SHA256 `kdf_id` 0x0001, ChaCha20-Poly1305 `aead_id` 0x0003 (CryptoKit `.Curve25519_SHA256_ChachaPoly`).

| Field | Contents |
| --- | --- |
| `info_text`, `info` | the client context's info, `localflow remote v1`, as text and hex |
| `server_private_key`, `server_public_key` | the server identity key pair (raw 32-byte X25519 scalar and public key) |
| `reply_private_key`, `reply_public_key` | the client's per-channel reply key pair named in the hello |
| `hello.enc` | the client's encapsulated key (32 bytes) |
| `hello.seq`, `hello.aad` | `0`, and the AAD `"LFR1"` ‖ seq as 8 bytes big-endian |
| `hello.plaintext` | the hello JSON (a `session` hello); the hello has **no** kind byte |
| `hello.frame` | the whole first client message: `"LFR1"` ‖ enc ‖ seq ‖ ciphertext |
| `exports.s2c_info` | `Export("localflow v1 s2c info", 32)` on the client-to-server context (`s2c_info_label` holds the label) |
| `exports.binding` | `Export("localflow v1 binding", 32)` on the client-to-server context (`binding_label`) |
| `server_first.enc` | the server-to-client encapsulated key `enc_s2c` |
| `server_first.seq`, `.aad` | `0`, and the AAD: seq as 8 bytes big-endian |
| `server_first.plaintext` | kind byte `00` followed by the `ready` JSON |
| `server_first.frame` | the whole first server message: enc_s2c ‖ seq ‖ ciphertext |
| `c2s[]` | client frames seq 1…3: `{seq, kind, aad, plaintext, frame}`; `plaintext` includes the kind byte, `frame` is seq ‖ ciphertext. Seq 1 is a control `dictation_start`, seq 2 an audio frame of four f32le samples, seq 3 a control `dictation_end` |
| `s2c[]` | server frames seq 1…3 in the same shape: `dictation_accepted`, `window_result`, `dictation_complete` |

CryptoKit's `HPKE.Sender` cannot take an injected ephemeral key, so the Swift test verifies these vectors as a recipient on both sides rather than re-sealing them:

1. As the server: `HPKE.Recipient(privateKey: server_private_key, ciphersuite:, info: info, encapsulatedKey: hello.enc)`, open `hello.frame[44...]` with `hello.aad`, compare with `hello.plaintext`, check both exports, then open every `c2s[].frame[8...]` in order with its `aad`.
2. As the client: `HPKE.Recipient(privateKey: reply_private_key, ciphersuite:, info: exports.s2c_info, encapsulatedKey: server_first.enc)`, open `server_first.frame[40...]` with `server_first.aad`, then every `s2c[].frame[8...]` in order.

The Go test performs the same two checks with `crypto/hpke` directly, independent of the `Channel` type.

## `messages/`

JSON examples for `protocol/schemas/remote-identity.schema.json`, `remote-hello.schema.json` and `remote-message.schema.json`. `scripts/validate-foundation.py` checks them against the schemas; `server/internal/remote/protocol_test.go` decodes every file.

- `messages/valid/<type>.json` must decode; `<type>-<variant>.json` is a further valid variant (for example `enrolled-rejected.json`, `dictation_start-no-boost.json`, `error-hello.json`).
- `messages/invalid/<type>-<reason>.json` must be refused. The expected channel error code is `unsupported_version` when the reason is `unsupported-version`, `limit_exceeded` when it is `limit-exceeded`, and `invalid_message` otherwise.
- `<type>` is the message `type` (`ready`, `enroll`, …, `error`; underscores kept), or `hello` and `identity` for the other two schemas. The type is everything before the first `-`. Hellos have one valid file per purpose: `hello-enroll.json`, `hello-refresh.json`, `hello-session.json`.

Every one of the 16 control message types has at least one valid and one invalid example. Byte bounds that JSON Schema cannot express (a term over 128 UTF-8 bytes but under 128 characters, device names with control characters) are covered in the Go and Swift unit tests instead. Tokens, keys, signatures and the ID token in these files are made-up values; the device key is the P-256 generator point.

## `worker-frames/`

Byte fixtures for the flowd ↔ speech worker framing, shared by `server/internal/speech` and `SpeechWorkerFramingTests` (`contracts/speech-worker-ipc.md`).

## `test-jwks.json` and `test-signing-key.pem`

A JWKS with one RS256 key, `kid` `localflow-test-1`, and its 2048-bit RSA private key (PKCS #8 PEM). The debug-build OIDC issuer (`--test-issuer`, `--test-jwks`, `-tags localflow_debug` only) signs ID tokens with the private key so enrollment tests run without Apple or Google. The key was generated once for this repository and is public by design.
