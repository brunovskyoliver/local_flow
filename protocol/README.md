# Shared protocol design

Feature 001 is offline and has no API dependency. The provisional `meeting.schema.json` and `summary.schema.json` shapes were removed in Feature 011, superseded by the analysis protocol below.

## Rewrite protocol v1 (Feature 003)

`openapi.yaml` declares `GET /v1/rewrite/health` and `POST /v1/rewrite`. The request body is `schemas/rewrite-request.schema.json` (six fields, `additionalProperties: false`); the response is `application/x-ndjson` where each line matches `schemas/rewrite-event.schema.json` (`accepted`, `progress`, `delta`, `result`, `error`). Every `result` carries the identity fields `server`, `backend`, `prompt_version`, `shield` and `timing` so stored attempts and corpus results are reproducible. Normative limits, status mapping and the client's nine validation rules are in `specs/003-server-rewriting/contracts/rewrite-protocol.md`; the Swift types live in `apps/macos/LocalFlow/Core/Rewrite/RewriteProtocol.swift` and the Go types in `server/internal/rewrite/protocol.go`, each with tests for every rejection.

## Rewrite protocol v2 (Feature 012)

A `schema_version: 2` request is the v1 body plus one required `context` object, `schemas/rewrite-context.schema.json`: the client's canonical, redacted snapshot of the focused app and field (sorted keys, no whitespace, absent parts omitted; servers also accept `null` for `app_name`, `window_title`, `before_cursor`, `after_cursor` and `selected_text`). The context is at most 8,192 bytes, its field set is closed, and each part has its own bound. A v2 request without `context`, a v1 request with it, or a context that breaks a bound is `invalid_request`; a version the server does not list in health `protocol_versions` is `unsupported_version`. flowd advertises `[1, 2]` by default (`--rewrite-protocol-versions`).

flowd puts the context in the system message after the mode template and the versioned context rules, as JSON inside `<screen_context>` … `</screen_context>` with every `<` written as the JSON escape `\u003c`, so no value can close the tag. The dictation stays the user message and only it is shielded. The `result` event keeps `schema_version: 1` and adds `context_prompt_version`, present only for v2. flowd logs `context_bytes` and never the context. Normative rules are in `specs/012-app-context-awareness/contracts/rewrite-protocol-v2.md` and ADR 0023.

Breaking wire changes require a new schema_version and explicit migration/compatibility design. Render Markdown/UI only after structural and semantic validation. No generated clients or schema framework yet.

## Analysis service (Feature 011)

`openapi.yaml` also declares `GET /v1/analysis/health` and `POST /v1/analysis/meeting`, served by the same flowd listener as a second, background-priority service. The request body is `schemas/analysis-request.schema.json`; the NDJSON response lines match `schemas/analysis-event.schema.json` (`accepted`, `progress`, `result`, `error`); the `analysis` object of a `result` line is `schemas/analysis-result.schema.json` (`schema_version` 1).

- Events: `accepted` → `progress`* → exactly one `result` or `error`. A `result` carries server, backend, prompt and pipeline identity plus timing and `preemptions`.
- Error codes: `unauthorized` (401/403), `invalid_request` (400), `too_large` (413), `unsupported_version` (400), `server_busy` (429), `queue_timeout`, `preempted`, `backend_unavailable`, `backend_timeout`, `backend_first_token_timeout`, `backend_error`, `output_too_large`, `output_invalid`, `source_validation`. `message` is one fixed sentence per code; backend text is never forwarded.
- Bounds: request body ≤ 262,144 bytes; each response line ≤ 98,304 bytes and the whole response stream ≤ 524,288 bytes (room for a progress line every 250 ms over the client's 300 s request timeout plus the result line; the client stops reading beyond either); per-request input text ≤ the advertised `limits.input_bytes`; one analysis slot by default; a rewrite-first gate and `--analysis-preempt` keep dictation ahead of analysis.
- Compatibility: a flowd without the service answers 404 → the client maps it to `server_unavailable`; `result_schema_version ≠ 1` in health refuses runs with `unsupported_version`; additive optional fields are a minor change; removing, renaming, re-typing or changing an enum bumps `schema_version`.

Normative rules are in `specs/011-meeting-intelligence/contracts/analysis-protocol.md`; the Swift types live in `apps/macos/LocalFlow/Core/Intelligence/AnalysisProtocol.swift` and the Go types in `server/internal/analysis/`, each with tests for every rejection.

## Remote channel v1 (Feature 014)

flowd's second listener (`--remote-listen`, loopback only, behind the owner's Cloudflare Tunnel) serves `GET /v1/remote/identity` and the WebSocket `GET /v1/remote/channel`, nothing else. Three schemas describe its JSON; framing, HPKE and sequence rules are not JSON and live only in the contract.

- `schemas/remote-identity.schema.json`: the public identity response (`schema_version` 1, `server` `flowd/<version>`, `protocol_versions`, the fixed `suite` `x25519-hkdfsha256-chacha20poly1305`, `server_key` as base64url without padding and the eight-group `fingerprint`). The client pins `server_key` at enrollment.
- `schemas/remote-hello.schema.json`: the plaintext of the sealed first client frame. `purpose` is `enroll`, `refresh` or `session`; `access_token` (`lfa_…`) is required for `session` and forbidden otherwise; `reply_key` is the client's per-channel X25519 public key.
- `schemas/remote-message.schema.json`: every later control message, `oneOf` by `type` over `ready`, `enroll`, `enrolled`, `refresh`, `tokens`, `dictation_start`, `dictation_accepted`, `window_result`, `progress`, `dictation_end`, `dictation_cancel`, `dictation_complete`, `cancelled`, `rewrite`, `rewrite_event` and `error`. Each has `schema_version` 1 and a closed field set; operations carry `op` (integer 1…2,147,483,647). `rewrite` and `rewrite_event` embed the unchanged rewrite request and event schemas above.

Error codes: `unauthorized`, `token_expired`, `not_approved`, `revoked`, `busy`, `invalid_message`, `unsupported_version`, `limit_exceeded`, `worker_unavailable`, `internal`, each with one fixed message sentence. Byte bounds JSON Schema cannot state (control message ≤ 65,536 bytes, device name ≤ 64 UTF-8 bytes after control characters are removed, boost terms ≤ 128 UTF-8 bytes, `device_key` a valid uncompressed P-256 point) are enforced by both implementations. Valid and invalid examples for every type are in `fixtures/remote/messages/` and `scripts/validate-foundation.py` checks them against these schemas. Normative rules are in `specs/014-remote-dictation-server/contracts/remote-channel.md`; the Go types live in `server/internal/remote/protocol.go` and the Swift types in `apps/macos/LocalFlow/Core/Remote/RemoteProtocol.swift`.

## Remote channel additions (Feature 018)

Summaries and meeting work run on the same channel. `protocol_versions` stays `[1]` and every addition is optional: a client that never sends the new messages behaves as under Feature 014. `schemas/remote-message.schema.json` adds the types below (each with `schema_version` 1, a closed field set and an `op`) and the optional `ready.capabilities`; `fixtures/remote/messages/` has valid and invalid examples of each. A device may hold 3 channels (was 2); the client uses them as interactive, live and background roles, and the server enforces only the count and one op at a time per channel. Feature 020 raises the count to 4 for a Mac's `handoff_watch` channel (`specs/020-ios-meeting-recording/contracts/handoff-v2.md`).

- Frame kind `0x02`: meeting samples, 16 kHz mono s16le, 1–32,000 samples (64,000 bytes) per frame. Accepted only while a `live_window` or `meeting_job` collects samples; anywhere else, and for an over-limit or odd-length frame, the op closes with `invalid_message`. Kinds `0x00` (control, ≤ 65,536 bytes) and `0x01` (dictation f32le, ≤ 16,000 samples) are unchanged.
- `ready.capabilities`: `ops` (the server's registered ops, at most 16 distinct names; today `dictation_start`, `rewrite`, `analysis`, `live_window` and `meeting_job`), `meeting_jobs` (`transcribe`, `diarize`, `embed`; empty while the meeting worker is unavailable) and `models` with the `transcription`, `diarization` and `voice` identities (`engine`, `model_id`, `model_revision`, `manifest_hash`; `voice` adds `dimension`, 0–4,096). No `capabilities` means a Feature 014 server: `dictation_start` and `rewrite` only.
- Summaries, client → server: `analysis_part` (`op`, `index` from 0, `data` ≤ 49,152 bytes) carries the UTF-8 JSON request of the analysis service above in order; `analysis` (`op`, `parts` 1–64, `bytes`, `sha256` lowercase hex) closes it. The assembled request is at most 262,144 bytes; a larger one or a larger fragment is `limit_exceeded`, a count, size or hash mismatch `invalid_message`. Only fragment 0 starts an op.
- Summaries, server → client: `analysis_event` carries one event of the analysis service (`accepted`, `progress`, `result`, `error`) inline as `event`, or closes its `analysis_event_part` fragments (`op`, `index`, `data` ≤ 49,152 bytes) with `parts` (1–64) and `sha256`. The op ends with the terminal `result` or `error`. One analysis per user at a time; the server uses its own backend and accepts no client-named primary server.
- Live preview: `live_window` (`op`, `sample_count` 1–96,000, `format` `s16le`, optional `language`, `auto` or a 2–3 letter code), then exactly `sample_count` samples in `0x02` frames; `live_result` (`op`, `window` with `text`, `tokens` and optional `evidence` as in `window_result`, `recognition_ms` ≤ 600,000). Windows queue after dictation windows, round robin between users, with one waiting window per user; another one gets `busy`.
- Meeting jobs: `meeting_job` (`op`, `kind`, `sample_count`, `format` `s16le`) then the samples in `0x02` frames. `transcribe` takes 1–1,920,000 samples (120 s) and the options `language`, `vocabulary_terms` (≤ 256 terms of 1–128 bytes) and `pipeline` (≤ 128 bytes, echoed back); `diarize` takes 1–9,600,000 (10 min) and optional `num_speakers` (1–64); `embed` takes 48,000–320,000 (3–20 s) and no options. An option for another kind is `invalid_message`.
- `meeting_progress` (`op`, `state` `queued` or `running`, optional `position` 0–1,024) and `meeting_result` (`op`, `kind`, `result`, `processing_ms`, `model`). `result` is, per kind: `text`, `tokens`, `timings_available`, optional `language`, `retry_depth` (0–2) and `pipeline`; `turns` (`cluster`, `start`, `end`, optional `quality`; ≤ 20,000) and `centroids` (`cluster`, `vector`; ≤ 256 clusters); or `vector` (1–4,096 values) and `speech_seconds`. `meeting_result` is never fragmented.
- `meeting_cancel` (`op`) ends a job; the server deletes its samples then, when the result is sent, or when the job fails. Limits: per user 1 running and 2 waiting jobs, 4 running meeting jobs on the server, and a 300 s worker deadline. A job starts only while no dictation window and no rewrite is in flight. `busy` at capacity; `worker_unavailable` while the meeting worker is down or lacks a model.

New error code `not_offered`: the server does not serve this op or job kind, and the client uses its local path until the next `ready`. For meeting work and summaries, `busy` and `worker_unavailable` mean wait and retry; for dictation they still mean local fallback. An `op` that does not belong to the channel's running op, including another user's, gets `invalid_message` and a `cross_user_attempt` audit row. Normative rules are in `specs/018-one-server/contracts/remote-channel.md`; the types live in `server/internal/remote/protocol.go` and `apps/macos/LocalFlow/Core/Remote/RemoteProtocol.swift`.
